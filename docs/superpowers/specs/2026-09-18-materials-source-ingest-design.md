# 本地知识库 / 项目 → 素材库接入

日期：2026-09-18
状态：待用户审阅
范围：第一刀。账号设定里登记本机来源，提炼成短卡片进现有素材库；写作只召回卡片，不现搜原文。

## 问题

素材库今天只接受作者手填的短事实（经历 / 数据 / 案例 / 金句 / 观察）。写作按题材字面召回最多 6 条，单条正文 ≤ 4000 字，规则是「栏目素材 + 素材库是全篇唯一可信的事实来源」。

作者的真实弹药在本机另外两层：

- 七个 Obsidian vault（`D:\Obsidian\…`）：亲历（客户沟通、自创框架）和第三方报告混在一起。
- 若干项目仓：分三类——验证中的 vibe coding demo、已交付/已上线、仓里已有产品文档。验证中的仓几乎没有 PRD，脚手架 README 不能当产品说明。

把整库或 `.ts` 灌进素材表会冲垮召回，也会把 McKinsey 的数字写成「我调研发现」，把 demo 写成已上线产品。

## 目标

1. 在账号下登记本机来源（知识库文件夹 / 项目文件夹），不监听文件、不自动重扫。
2. 按来源类型提炼短卡片，**入库前必须过目**。
3. 亲历进现有五类；第三方报告进新类「引用」，成稿里必须点名来源。
4. 项目先定类别，验证中先起草成果说明、确认后再抽卡。
5. 写作仍只召回已入库卡片；亲历和引用分块进提示词，名额拆开。

非目标（第一刀明确不做）：向量检索、写作时现搜原文、文件监听、把成果说明写回 git、自动猜项目类别、浏览器读盘 / 上传 zip、跨账号共享来源。

## 约束（已拍板）

- 产品跑在作者本机 Node 上，路径是服务端本机绝对路径（例如 `D:\Obsidian\EA-Knowledge-Vault`）。
- 类别由作者标，系统不猜「验证中 vs 已交付」。
- 卡片是事实层：作者能在素材库里看见、改、删。
- 重扫不覆盖作者改过的卡片，只追加新抽出的。
- 客户真名在入库时处理，写作不再二次改写。

## 1. 来源模型

素材仍挂在 persona 上。来源单独建表 `material_sources`，不塞进 `personas` JSON。

### 1.1 字段

| 字段 | 含义 |
|---|---|
| `kind` | `vault`（知识库目录）或 `project`（项目目录） |
| `path` | 本机绝对路径，必须是已存在的目录 |
| `label` | 显示名，默认文件夹名 |
| `project_class` | 仅 project：`validating` / `delivered` / `has_docs` |
| `doc_path` | 可选文件路径。`has_docs` 必填，指向产品文档；另外两类确认成果说明后可指向该说明的落点（第一刀说明只存在数据库，不写回仓库） |
| `brief` | 系统起草、作者改过的成果说明（markdown 文本） |
| `brief_status` | `none` / `draft` / `confirmed` |
| `enabled` | 关掉不参与扫描和提炼 |
| `preview_json` | 当前这一轮抽出、尚未入库的卡片预览 |
| `last_error` | 最近一次失败原因（路径读不到、模型失败等），成功则清空 |
| `last_scan_at` | 最近一次扫描时间 |

同一 persona 下同一 `path` 不可重复。

### 1.2 UI

账号设定现有板块：基本设定 / 个人人设 / 素材库 / 语气样本。加第四个需先保存账号的板块：**来源**。

操作：添加路径、选 kind、项目再选三类之一、`has_docs` 时填文档路径、启用/停用、删除来源、点「扫描/提炼」。

来源行上显示：label、类别、brief 状态、上次错误（标红）、已入库卡片数（按 `source_id` 计）。

### 1.3 扫描范围

- vault：递归 `.md`。跳过目录名 / 路径段：`.obsidian`、`.git`、`00_MOC`、`90_模板`。
- project：不扫 `node_modules`、`.git`、`dist`、`build`、`.next`、`coverage`。
  - `has_docs`：**只读 `doc_path` 那一个文件**，不读代码。
  - `delivered` 且填了 `doc_path`：同样只读该文件，不起草说明。
  - `validating`，或 `delivered` 且没有 `doc_path`：成果说明未 `confirmed` 时禁止抽卡；确认后只从 `brief` 抽，仍不把 `.ts` 当素材。
  - 起草说明时读仓，不是全量源码。只取：根目录 README、`package.json` 的 name/description、`src/types*`、`src/data/**` 的入口文件、`src/App.*` / `app/page.*`。最多 12 个文件、合计 30 000 字；再多截断并在说明顶部注明。

单文件超过 20 000 字时，送进抽卡模型的只取前 12 000 字（预览里注明「已截断」）。

路径校验：绝对路径、存在、目录（`doc_path` 则必须是文件）。读不到则来源标红，不改已有素材。

## 2. 抽卡流水线

一次提炼两段，中间都过目。系统不直接 `INSERT` 进 `materials`。

### 2.1 项目：先说明，再抽卡

点「扫描/提炼」时看 `project_class`：

| 类别 | 先做什么 | 再抽什么 |
|---|---|---|
| `validating` | 按 1.3 取样读仓，起草成果说明 → `brief_status=draft` | 作者改完并确认后，从 `brief` 抽「我做了 X 来验证 Y」 |
| `delivered` 且没有 `doc_path` | 同样起草，模板换成产品说明 | 从确认后的说明抽产品事实卡 |
| `has_docs`，或 `delivered` 且有 `doc_path` | 不读代码、不起草 | 从 `doc_path` 抽 |

`validating` 说明模板固定栏，模型必须填、作者可改：

- 项目名
- 验证的想法（一句话）
- 做成了什么（能跑的部分，禁止写用户数/已上线/已交付）
- 学到了什么
- 明确一句：**这是验证用 demo，不是产品**

`delivered` 模板：是什么 / 给谁用 / 上了什么 / 效果如何。没有的栏留空，不许编。

确认按钮把 `brief_status` 设为 `confirmed`。未确认时来源上的主按钮文案是「先确认成果说明」，抽卡 API 返回 400。

第一刀成果说明**只存在 `brief` 字段**，不写回项目仓库。

### 2.2 知识库：先分类，再抽短卡

分类用路径和笔记元数据，不靠模型猜「这是不是亲历」：

**定为引用（整篇默认抽「引用」卡）**，满足任一：

- 路径含 `30_行业研究`、`99_素材源`、`行业研究`、`素材源`
- 标签含 `素材/报告` 或 `报告`
- frontmatter `source` 指向 pdf / 第三方文件名

**定为亲历（整篇默认抽现有五类）**，满足任一：

- 路径含 `20_案例`、`客户`、`项目实践`
- 笔记是第一人称经历、客户沟通

一篇可以两类都有（例如门控设计溯源里既有混沌白皮书又有作者自己的设计）。模型按条输出卡，每张自带 `kind`；服务端再校验：`kind=引用` 必须有非空 `cite`，否则预览里锁定为不可入库。

抽卡模型输入：笔记正文（或项目 brief）。输出一组短卡，每张：

```
kind, title (≤80字), body (≤4000字), tags, cite, source_ref
```

McKinsey「六大发现」这类应变多张引用卡，每张一个论断/数字 + `cite`（如「McKinsey, The State of AI 2025」）。禁止把整篇笔记塞进一张卡。

### 2.3 预览入库（两种来源共用）

抽出的卡写入该来源的 `preview_json`（再扫一次会整份覆盖预览，不影响已入库卡）。界面列表：类型、标题、正文、标签、cite、来源相对路径、截断标记。

单次 extract 最多处理 40 个文件；超出的在来源行提示「未扫完，可下次再扫」，不静默丢弃。

作者可以：改类型 / 改文案 / 改 cite / 去掉勾选。点「入库」只插入仍勾选、且通过校验的卡。

**公开稿匿名**：每张卡一个勾选。亲历默认开，引用默认关。勾选的卡在 INSERT 前走一次短 LLM 改写：公司名、人名换成类别描述（「温氏」→「一家农牧企业」），数字和机制不动。改写失败则入库原文，并在响应里列出哪些卡没匿名成功，作者可再手改。匿名发生在入库时，素材库里存的就是最终正文。

校验（勾不上或入库拒绝）：

- title / body 为空
- `kind=引用` 且 `cite` 为空
- `kind=引用` 且 `cite` 像「我调研」「内部数据」这种无第三方出处

### 2.4 去重与重扫

`materials` 增加：

| 字段 | 含义 |
|---|---|
| `source_id` | 来源 id，手填的卡为 null |
| `source_ref` | 来源内相对路径，项目 brief 用 `__brief__` |
| `cite` | 引用出处名；亲历为空 |
| `user_edited` | 作者在素材库里保存过则为 1 |

去重键：`(source_id, source_ref, title)`。重扫时：

- 已有且 `user_edited=1`：不覆盖
- 已有且未改：不覆盖（避免作者没改也被模型换一种写法）；只追加**标题尚未出现**的新卡
- 预览里标明「将跳过（已在库中）」

素材库手动保存（现有 PUT）把 `user_edited` 置 1。

`MATERIAL_KINDS` 变为 `['经历', '数据', '案例', '金句', '观察', '引用']`。手填仍可用这六类；「引用」手填时同样要求 `cite`。

## 3. 写作时召回

写作**只召回已入库卡片**。不在成稿时打开知识库或项目目录。

选题（三个方向）仍然不召回，避免方向围着几张卡转。召回只发生在成稿 `handleContent`，以及成稿检查（见下）。

### 3.1 算法

沿用现在的 2 字滑窗、标签命中权重 ×2、得分 < 3 丢弃。查询文本仍是题材 + 标题 + 角度 + 提纲。

名额拆开，合计 ≤ 6：

- 亲历五类：最多 4
- 引用：最多 2
- 某一边不够，名额**不**匀给另一边

两边各自按分排序后截断。`markUsed` 仍给实际召回的 id。

### 3.2 提示词

`materialsBlock` 拆成两块。`contentUser` 两块都拼进去。

**亲历**（现有措辞，略收紧）：作者本人积累的真实素材，唯一可信的个人事实；用得上就展开，用不上不硬塞；不许编造之外的经历、时间、数字、职位、人物。

**引用**（新块）：

- 用到必须点名 `cite`（写成「McKinsey 2025 年 State of AI 报告」这种可读出处，不要只丢文件名）
- 不许写成作者亲测、作者客户、或「我调研发现」
- 用不上不硬塞
- 数字必须与卡片一致，不许改成更好看的数

`CONTENT_SYSTEM` 加一条：若给了引用块，引用里的事实只能作为带出处的论据，不能转成第一人称经历。

### 3.3 成稿检查

`reviewUser` 成稿时再跑一次同样的召回（题材 + 成稿标题），把引用卡的 `cite` + 论断摘要拼进检查上下文。

「事实存疑」补充：正文出现具体数字/研究结论，和已给引用对得上但没点名出处的，报高；对不上任何引用、也没有其它可核查出处的，仍按现有规则报。

匿名不在写作期处理：卡片正文是什么就用什么。

## 4. 失败与第一刀验收

### 4.1 失败

能继续的继续；不能抽就不入库；原因写在来源行上，不连环 toast。

| 情况 | 处理 |
|---|---|
| 路径不存在 / 没权限 | 来源标红「路径读不到」，不扫 |
| vault 0 篇可用 md | 提示跳过 MOC/模板/点目录之后为空 |
| 验证中 / 无文档的已交付，说明未确认 | 不抽卡，按钮为「先确认成果说明」 |
| `has_docs` 但 `doc_path` 空或不是文件 | 不读代码凑数，提示补文档路径 |
| 单篇抽卡模型失败 | 跳过该篇，预览里记失败数，其余继续 |
| 整次提炼模型失败 | 不写 `preview_json`；已有素材不动 |
| 引用无 cite / 正文空 | 预览锁定不可入库 |
| 重扫撞上已有卡 | 不覆盖，只追加新标题 |
| 写作召回 0 条 | 与现在相同，不塞空块 |

抽卡走现有 LLM 通道；失败时的演示/mock 模式给出可辨认的占位卡（带 `cite=演示`），避免无密钥时整条流水线卡死。

### 4.2 第一刀做 / 不做

做：来源 CRUD、项目成果说明过目、vault/项目抽卡预览入库、`引用` 类、成稿召回拆亲历/引用、入库时匿名勾选、检查上下文带引用。

不做：见文首非目标。

### 4.3 验收

1. 挂 `D:\Obsidian\AI-TRANSFORMATION-Knowledge-Vault`：`30_行业研究/McKinsey-StateOfAI-2025.md` 必须出「引用」卡且 `cite` 含 McKinsey；`10_转型方法论/评估体系/业务准入门控.md` 能拆出引用（混沌白皮书）和亲历（门控设计）。
2. 挂 `D:\AI\vibe-coding-all-projects-pm\AI-maturity-tools`，标 `validating`：先出成果说明；未确认时素材库 +0；确认后再抽，卡里不得出现「已上线」「用户」「PRD」。
3. 同一文件扫两遍：改过标题的卡仍在，不回到模型原文。
4. 写题材含「AI 成熟度 / Agent 渗透率」：召回亲历 ≤4、引用 ≤2；成稿里 McKinsey 数字必须点名，不能写成「我调研发现」。
5. 路径填错：来源标红，素材表不变。

## 5. 数据与接口

### 5.1 表

`material_sources` 新建。`materials` 用现有 `PRAGMA table_info` + `ALTER TABLE` 加列（与 `drafts.metrics_json` 同一套路），新库 `CREATE TABLE` 直接带这些列。

索引：`idx_sources_persona (user_id, persona_id, id DESC)`；`idx_materials_source (source_id, source_ref)`。

删除来源：`materials.source_id` 置空，卡片保留（作者已过目的事实不跟来源一起消失）。停用来源：不参与新的提炼；已入库卡仍参与召回，除非作者手动删。

### 5.2 API

均需登录，且 persona / source / material 属于当前用户。

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/personas/:id/sources` | 来源列表（含 brief 状态、错误、入库条数） |
| POST | `/api/personas/:id/sources` | 登记来源 |
| PUT | `/api/sources/:sid` | 改 label / class / doc_path / enabled |
| DELETE | `/api/sources/:sid` | 删来源，卡片 source_id 置空 |
| POST | `/api/sources/:sid/brief` | 起草或覆盖成果说明（仅 project 且非 has_docs） |
| PUT | `/api/sources/:sid/brief` | 保存作者修改；`{confirm:true}` 时 confirmed |
| POST | `/api/sources/:sid/extract` | 扫描并抽卡 → `preview_json`（SSE 进度：当前文件 / 失败数） |
| POST | `/api/sources/:sid/commit` | 把预览里勾选且合法的卡 INSERT |

现有 materials CRUD 不变；create/update 接受可选 `cite`，`kind=引用` 时必填；update 置 `user_edited=1`。

### 5.3 主要改动文件

- `server/db.js` — 表、kinds、Materials 增列、Sources
- `server/routes.js` — 来源 API、`recallMaterials` 拆名额、content/review 传入分组
- `server/prompts.js` — 亲历块 / 引用块、抽卡与成果说明的 system/user、CONTENT_SYSTEM、REVIEW 事实存疑
- `server/index.js` — 路由
- `public/index.html` / `public/app.js` — 来源板块、预览、匿名勾选
- 抽卡 / 读盘逻辑单独放 `server/sourceingest.js`，不要继续堆进已很大的 `routes.js`

## 6. 抽卡与说明的模型约定

走现有 `llm.js` 通道。抽卡用结构化输出（与选题 JSON schema 同一套路）。

成果说明：非结构化 markdown，按模板小标题输出。服务端检查 `validating` 的说明是否含「demo / 验证」类声明；没有则在 UI 警告，但不阻断确认（作者可能改了措辞）。

单次 extract：按文件串行，避免把整个 vault 一次性塞进上下文。进度用 SSE。

## 7. 明确的产品判断

- 知识库是弹药箱，素材库是经过作者签字的事实层。写作只信后者。
- 项目类别是作者的判断；系统只负责按类别用不同模板，并把「未确认说明」当成硬闸。
- 引用不是二等亲历。少给（最多 2 条）是为了防止报告挤掉「我做了什么」。
- 第一刀宁可变慢、要过目，也不要静默灌库。
